# Function Calling 协议稳定性实验报告

## 背景

Agent 执行循环通过 `LlmClient` 协议隔离了两种工具调用协议:function calling(模型侧结构化输出)与 ReAct 文本协议(提示词约定格式)。SUT 需在两者间选定主协议 —— 判定标准:function calling 的稳定性是否足以支撑轨迹评测(评测对"调没调工具、参数对不对"的断言依赖协议输出的可靠性)。

## 方法

- 10 个代表性任务覆盖全部八类场景(single_tool / multi_tool_chain / rag_plus_tool / no_tool / missing_slot / fault_recovery / adversarial ×2 / multi_intent)
- 每任务执行 3 遍,temperature=0,同任务期望判定完全一致
- 双指标:
  - **轨迹完成率**(主指标):各任务期望(工具链、世界终态、答案语义、零变更约束)通过数 / 总执行数
  - **协议故障率**:LLM 客户端统计的 arguments JSON 解析失败数、空参数数
- 决策阈值:完成率 ≥ 80% → 维持 function calling;否则切文本协议

## 结果

| 指标 | 数值 |
|------|------|
| 轨迹完成率 | **30 / 30 = 100%** |
| LLM 请求次数 | 63 |
| 工具调用次数 | 36 |
| arguments 解析失败 | **0** |
| 空参数调用 | **0** |
| 三轮间行为漂移 | 无(temperature=0 下逐轮一致) |

明细数据:[fc_stability.json](fc_stability.json)(每条执行含步骤序列、答案摘要、判定理由)。

## 决策

**维持 function calling。** 协议层零故障,完成率远超阈值;文本协议分支保留在适配层,不删除。

## 实验过程中的三个发现(比结论更有价值)

1. **任务措辞的假设语气会触发征询行为**:"要是退的话扣多少"这类假设性表述,模型会先确认"需要我帮您算吗"再行动 —— 对任务集设计的启示:**一个任务只表达一个明确意图,避免歧义措辞**,否则测的是措辞而不是能力。
2. **模型的追问语用不工具化**:glm-4-flash 缺槽位时倾向直接文字追问而非调用 ask_user 元工具(提示词与工具描述双强化均不改变)。评测契约按真实行为设计:missing_slot 的判定底线是**零盲调写工具 + 答案含追问语义**,不强求追问走工具通道。
3. **全半角标点是答案断言的现实坑**:以"?"判追问语义时,半角列表匹配不上全角输出。答案关键词断言应使用纯语义关键词并先做归一化(去空白、剥句末标点),不依赖标点形态。
