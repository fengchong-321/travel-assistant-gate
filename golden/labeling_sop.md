# golden 标注 SOP

> 一条任务 = 一个用户意图 + 四维期望。标注质量决定评测质量;本 SOP 的
> 每条纪律都来自真实踩坑,标注前通读,评审时对照。

## 0. 标心:按应然标注,不迁就 SUT

期望描述「正确 Agent 应该怎么做」,不是「当前 Agent 恰好怎么做」。跑挂了
先归因三分(见 §6),唯独不允许"改期望凑分数"。

## 1. 一条任务一个明确意图

复合诉求拆成 multi_intent 类显式标注,不要让一条 case 背两个模糊意图。
假设语气("能不能帮我…")会被 SUT 理解为征询,测确认行为时才用它。

## 2. 四维期望的取舍

| 维度 | 何时严 | 何时松 |
|---|---|---|
| tools.exact_seq | 正常业务链(查→算→建) | 失败路径用 free(实现自由) |
| tools.any_of | 同一信息有等价来源(开放时间:知识库/公告接口),任一路径即对 | 单一来源场景不用(会放过漏调) |
| tools.forbidden | 对抗/缺槽类:写工具出现即否决 | 正常链不给 forbidden |
| expected_args | 关键业务参数(订单号/金额/日期) | 展示性参数不标 |
| trajectory.order | 顺序即安全的链(先算费后建单) | 只读链不标顺序 |
| world_assertions | **期望写操作成功的任务必带**(平台纪律,入库校验拦截) | 只读任务不带 |
| repeats | 写操作/对抗类标 3(pass^3) | 只读/纯检索标 1 |

## 3. answer_keywords 纪律(踩坑最多)

- **只用语义词,不碰标点**:全半角问号不同码点(`?`≠`?`)已实际踩坑;
- **预判表述变体,取语义交集**:"已使用"/"已经使用"→ 标「使用」;
  "未支付"/"还没付款"→ 标「付」;
- **数字最稳**:金额、张数、时间(144/160/50/20)比任何措辞词都稳;
- **禁词慎用**:answer_forbidden_keywords 是"编造比缺失更严重"的场景
  专用(如已使用订单的答案禁出现"退款成功"),不要当第二个关键词列表;
- 关键词 AND 语义:每多一个词,FAIL 面宽一分。问状态别要求金额(D6
  首跑教训:问状态答"已支付"是对的,标"288"属过度指定)。

## 4. plan_anchors 纪律

- 工具能确定的步骤**一律标工具锚**(tool + 可选 args_match):确定性
  命中,零 LLM 成本;
- 只有拒绝/追问/解释类实现自由的步骤标语义锚(tool 省略):这直接决定
  一轮评测的 judge 调用量上限,是成本设计的一部分;
- **语义锚描述写行为语义**,不用否定/自指表述:「拒绝使用不存在的工具」
  会被 judge 误读为"是否使用了该工具"→ 改「明确告知无法提供系统不
  支持的服务」(D7 实踩);
- 同一工具的两个实例用 args_match 区分(query_two_orders 的两单查询)。

## 5. 世界断言纪律

- 断言终态,不断言过程:改期断言 visit_date 与两日库存 sold,不断言
  中间是否查过库存;
- 金额断言给出精确值(手续费三档按 seed 时钟 2026-10-01 推演):
  ≥48h→0%,24-48h→20%,<24h→50%;
- 幂等用 count=1;防越权用双断言(状态未变 + refunds count=0)。

## 6. 跑挂后的归因三分法

FAIL 不等于 SUT 错,逐条定性再动手:

1. **SUT 缺陷** → golden 不动,记录发现(修 SUT 或留作已知);
2. **标注过度指定** → 改 golden(措辞变体/超出意图的硬性要求);
3. **评测器/锚点问题** → 修评测器(如 judge 解析、锚点歧义)。

判据:把 SUT 的答案拿给业务同学看 —— 业务说"这回答没问题",就是 2 或 3。

## 7. 入库与评审

- 新 case 入库跑 `uv run pytest tests/test_task_schema.py`:入库校验
  (类别配套/写操作必带世界断言/exact_seq 无重复)+ 自举断言全过;
- 评审 checklist:意图唯一?关键词过词面变体关?语义锚描述无歧义?
  写操作 repeats=3?世界断言可从 seed 推演?
